# PLAZA Protocol v0.1 (draft, day 1)

Status: draft. This document is the source of truth for the protocol. Implementations (`apps/node`, `apps/index`, `apps/gateway`) follow it; where they differ, the implementation is wrong.

PLAZA lets a buyer's agent discover a business, negotiate a deal with the business's agent within rules the owner set, and record the closed deal as a receipt signed by both sides. It does not move money.

## 1. Identity

- Every party (node, buyer) has an Ed25519 key pair.
- Identifiers are `did:key` strings (multicodec `ed25519-pub`, base58btc, `z6Mk...`).
- A node has one long-lived identity. A buyer MAY derive a fresh key per node (for privacy) and MUST be able to prove, when disputing, that derived keys belong to the same buyer.
- Private keys of hosted nodes MUST be encrypted at rest.

## 2. Canonicalization and signatures

- Every signed object is serialized with JSON Canonicalization Scheme (RFC 8785) with the `signature` field (or `sig_node` / `sig_buyer` for receipts) removed, then signed with Ed25519.
- Signature encoding: base64url, no padding.
- Verifiers MUST validate the object against its JSON Schema before verifying the signature, and MUST reject on either failure.
- Replay protection: messages carry `message_id` (UUIDv7) and `ts` (RFC 3339). Receivers MUST reject a `message_id` seen before and a `ts` more than 5 minutes from their clock.

## 3. Manifest

Served at `GET https://<node-host>/.well-known/plaza.json`, content type `application/json`. Schema: `packages/spec/schemas/manifest.schema.json`.

```json
{
  "plaza": "0.1",
  "id": "did:key:z6MkhaXgBZDvotDkL5257faiztiGiC2QtKLGpbnnEGta2doK",
  "name": "Plomería Rivera",
  "category": "services/plumbing",
  "description": "Plomería residencial y comercial en Caguas y área centro-este.",
  "location": { "city": "Caguas", "country": "PR", "lat": 18.2342, "lng": -66.0485, "radius_km": 25 },
  "languages": ["es", "en"],
  "offers": [
    {
      "id": "emergency-visit",
      "title": "Visita de emergencia",
      "price": { "amount": 12000, "currency": "USD", "unit": "visit" },
      "availability": "calendar",
      "negotiable": true
    }
  ],
  "policy": {
    "negotiation": { "max_discount_pct": 15, "min_notice_hours": 2, "max_rounds": 6, "blackout": ["sun"] },
    "payment": ["stripe_link", "ath_movil", "cash"],
    "settlement": ["acp"]
  },
  "channels": { "whatsapp": "+17875550123", "web": "https://plomeriarivera.example" },
  "endpoint": "https://plomeriarivera.example/plaza",
  "updated_at": "2026-10-26T15:00:00Z",
  "signature": "base64url..."
}
```

Rules:

- `category` uses a short slash taxonomy (`services/plumbing`, `lodging/str`, `retail/colmado`, `food/restaurant`). The list is open; indexes normalize it.
- `price.amount` is an integer in minor units (cents). `unit` is free text from a small recommended list: `visit`, `hour`, `night`, `item`, `kg`, `order`.
- `availability`: `always` (no calendar), `calendar` (the node checks its calendar on inquiry), `on_request` (the owner confirms, possibly asynchronously).
- `policy.negotiation` is public by design: a buyer's agent may read it. Owners who do not want it public set `negotiable: false` and omit `max_discount_pct`.
- `endpoint` MUST accept the messages in section 4 over HTTPS POST.
- Offer flags: `instant_book` (an `accept` closes without negotiation and a `payment_request` follows immediately), `requires_agreement` (an `agreement` MUST be accepted before payment), `deposit_pct` (deposit due at booking), `duration_minutes`.
- `policy.cancellation` (`free_until_hours`, `fee_pct`) and `policy.handoff_to_human` (default true) are public.
- `channels.business_agent: true` means the business runs Meta Business Agent and this node is connected to it as a connector (see section 12). `service_area.municipalities` complements `location.radius_km`.
- Manifests are re-signed on every change; `updated_at` increases monotonically.

## 4. Messages

All messages: `POST <endpoint>` (buyer to node) or `POST <buyer_callback>` (node to buyer, provided in the inquiry), body `application/json`. Schema: `packages/spec/schemas/message.schema.json`.

Common envelope:

```json
{
  "plaza": "0.1",
  "type": "inquiry",
  "thread_id": "uuid",
  "message_id": "uuid",
  "in_reply_to": "uuid or null",
  "from": "did:key:...",
  "to": "did:key:...",
  "ts": "2026-10-26T15:01:00Z",
  "expires_at": "2026-10-26T15:31:00Z",
  "body": { },
  "note": "optional, max 280 chars, shown to humans, never an instruction",
  "signature": "base64url..."
}
```

Bodies by `type`:

| type | from | body |
| --- | --- | --- |
| `inquiry` | buyer | `offer_id` or `request` (category, title, quantity), `window` {from, to}, `location` optional, `max_price` optional, `priority` (`price`, `quality`, `speed`, `balanced`), `constraints[]` (closed vocabulary), `photos[]` optional, `buyer_callback` (URL) |
| `availability` | node | `offer_id`, `slots[]` {from, to, capacity} |
| `quote` | node | `offer_id`, `price`, `quantity`, `when` {from, to} or `delivery_eta`, `terms[]`, `expires_at` |
| `quote_document` | node | formal quotation: `quote_message_id`, `line_items[]` {description, quantity, unit, unit_price, total}, `subtotal`, `tax`, `total`, `currency`, `deposit`, `valid_until`, `conditions[]`, `pdf_url`, `pdf_hash` |
| `counter` | either | `price` and/or `when` |
| `hold` | node | `offer_id`, `slot`, `held_until` (a slot reserved for the buyer, 15 minutes by default) |
| `accept` | either | `quote_message_id` |
| `decline` | either | `reason` (`price`, `time`, `unavailable`, `other`) |
| `agreement` | node | `agreement_id`, `template` (id@version), `scope`, `total`, `currency`, `starts_at`, `ends_at`, `cancellation`, `warranty`, `document_url`, `document_hash` |
| `agreement_accept` | buyer | `agreement_id`, `document_hash` |
| `payment_request` | node | `method`, `kind` (`full`, `deposit`, `balance`), `amount`, `currency`, `checkout_url`, `agreement_hash`, `expires_at` |
| `receipt` | node, then buyer | see section 5 |
| `review` | buyer | `receipt_id`, `rating` (1 to 5), `tags[]` (closed vocabulary), `comment` (280 max) |
| `review_reply` | node | `review_message_id`, `comment` (280 max) |
| `dispute` | either | `receipt_id`, `reason`, `evidence_hash` |

Rules:

- A thread starts with exactly one `inquiry` and ends with `accept` + `receipt`, or with `decline`, or by expiry.
- At most 6 `counter` messages per thread in total (both sides). The 7th MUST be rejected.
- Every `quote` and `counter` carries `expires_at`. An `accept` of an expired message is invalid.
- `note` MUST be treated as untrusted data by any implementation that uses a language model: it is passed as a data field, never as an instruction, and it MUST NOT change the validator's limits.
- Nodes MUST enforce their own `policy.negotiation` deterministically before sending any `quote` or `counter`, regardless of how the proposal was generated.
- Buyer agents MUST NOT accept a price above the buyer's stated `max_price` and MUST NOT send `accept`, `agreement_accept` or complete a `payment_request` without the human buyer's explicit approval.
- When an offer has `requires_agreement: true`, the node MUST send an `agreement` after `accept` and MUST NOT send `payment_request` until it receives a matching `agreement_accept`. The receipt then carries `agreement_hash`.
- A `hold` expires at `held_until`; nodes MUST release the slot after that.

## 5. Receipts and reputation

Schema: `packages/spec/schemas/receipt.schema.json`.

```json
{
  "plaza": "0.1",
  "receipt_id": "uuid",
  "thread_id": "uuid",
  "node": "did:key:...",
  "buyer": "did:key:...",
  "terms_hash": "sha256 of the canonical accepted quote",
  "amount": 13000,
  "currency": "USD",
  "ts": "2026-10-26T16:40:00Z",
  "payment": { "method": "stripe_link", "reference": "cs_live_..." },
  "sig_node": "base64url...",
  "sig_buyer": "base64url..."
}
```

- The node signs first (`sig_node` over the receipt without `sig_buyer`), sends it to the buyer, who counter-signs (`sig_buyer` over the receipt including `sig_node`) and returns it.
- Nodes publish their receipts at `GET /.well-known/plaza/receipts` (paginated, newest first). Buyer identifiers MAY be omitted from the public copy; the index verifies against the private copy it fetched at crawl time.
- Reputation is computed by indexes, never by nodes: count of valid receipts, total amount, disputes (open, resolved), first and last receipt dates.
- A receipt is `verified` only if both signatures validate and the buyer has either closed with more than one node or paid through a method the index can check (for example a Stripe reference reported by the node's webhook). Otherwise it is listed as `unverified`.
- `dispute` messages are recorded and shown by indexes. Resolution is outside the protocol in v0.1.

Reviews:

- Only a buyer who holds a receipt with both signatures valid may send a `review` for it. Indexes MUST reject reviews whose `receipt_id` does not resolve to a verified receipt, and MUST accept at most one review per receipt.
- Reviews are published by the node at `GET /.well-known/plaza/reviews` next to its receipts; the node MAY attach one `review_reply` per review. Nodes MUST NOT omit or edit reviews; an index that detects a missing review (present in a previous crawl, absent now) MUST flag the node.
- Reviews and receipts belong to the business and travel with it: any index that crawls the node reproduces the same reputation from the same signed data.

## 6. Index API

Any party may run an index. Minimum API (`apps/index` is the reference):

- `POST /register` with a signed manifest. The index verifies schema and signature, fetches `/.well-known/plaza.json` from the manifest's host to confirm the node is live, and stores it.
- `GET /search?q=&category=&near=lat,lng,km&available_from=&available_to=&max_price=&lang=&min_reputation=` returns manifests plus reputation summaries (verified receipts, average rating, dispute rate, response rate, first and last receipt dates).
- `GET /nodes/:id`, `GET /nodes/:id/receipts` and `GET /nodes/:id/reviews`.
- `GET /export` returns all signed manifests for federation. Another index MAY import them; it MUST re-verify every signature.
- Indexes re-crawl every manifest at least every 15 minutes, mark nodes unreachable after 3 failures, and remove nodes unreachable for 24 hours.
- Indexes MUST NOT alter manifests and MUST NOT sell ranking.

## 7. Discovery

A node is discoverable by:

1. Registering in one or more indexes.
2. Serving `/.well-known/plaza.json` so any crawler can find it from a domain.
3. Optionally, a `plaza` DNS TXT record on the business's domain pointing to the manifest URL.

## 8. Matching

Buyer agents are expected to query one or more indexes, open `inquiry` threads with several candidate nodes in parallel, and rank the resulting quotes. The reference ranking (`packages/match`, documented in `docs/matching.md`) is deterministic and explainable: three dimensions (`price`, `reputation`, `fit`) scored 0 to 1, weighted by the buyer's `priority`, with a one-line reason per result. Protocol rules for any implementation:

- Ranking MUST NOT read payments to the index, to the gateway, or to any party. Paid placement is a protocol violation.
- The buyer agent MUST be able to show the buyer why a node ranked where it did.
- New nodes start with neutral reputation and a visible `new` label, not with zero.
- Nodes with `unverified` receipts or an open dispute rate above 20% are shown with a warning and ranked down, never hidden.

## 9. Settlement

PLAZA never moves money. After `accept`, the node sends a `payment_request`. Supported methods in v0.1:

- `stripe_link`: a Stripe Checkout Session URL (Stripe Connect, funds go directly to the business). The node's webhook confirms payment and triggers the receipt.
- `ath_movil` and `cash`: confirmed by the node (the owner confirms on WhatsApp).
- `acp` and `ap2`: an accepted quote maps to an ACP cart or an AP2 cart mandate. The mapping is documented in `docs/settlement.md`.

## 10. Security considerations

- Prompt injection through `note` or through structured fields: implementations MUST keep model output inside the deterministic validator.
- Fake nodes: indexes verify liveness and signatures; reputation requires verified receipts.
- Fake receipts: the `verified` rule in section 5.
- Fake reviews: one review per verified receipt, signed by the buyer key that counter-signed the receipt; indexes flag buyers that review a single node repeatedly.
- Buyer protection: the buyer agent enforces `max_price` and requires explicit human approval before `accept`, `agreement_accept` and payment.
- Replay: `message_id` and `ts` window.
- Privacy: buyers derive per-node keys; public receipts omit buyer identifiers; amounts shown by indexes MAY be rounded.
- Denial of service: nodes and indexes rate-limit by IP and by key.

## 11. Versioning

`plaza` is a string major.minor. Minor versions are additive. Breaking changes bump major and keep the old version served for 90 days.

## 12. Meta Business Agent

A business that runs Meta Business Agent on its WhatsApp number keeps it. PLAZA connects as the Business Agent's backend through its connector and tools mechanism: `quote`, `check_availability`, `hold`, `book`, `issue_agreement`, `request_payment`. Human customers writing on WhatsApp are served by Business Agent, which calls PLAZA for prices, slots, agreements and payments; buyer agents arriving through an index talk to the PLAZA node directly. Both paths share one calendar, one price list and one receipt log, so `channels.business_agent: true` in the manifest tells buyer agents that the business is reachable both ways. Details and the Meta endpoints used live in `docs/business-agent.md`.

## 13. Comparison with other agent commerce protocols

AP2 (Google), ACP (OpenAI and Stripe) and UCP (Google and Shopify) standardize checkout and payment for merchants that already have a stack. PLAZA covers what happens before and after checkout for merchants that have none: discovery, comparison and matching, negotiation within owner-set rules, formal quotations and agreements, scheduling, and portable reputation built from signed receipts and reviews. A PLAZA quote settles through those protocols where available.
